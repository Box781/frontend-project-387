# План развития

Продукт уже умеет записывать гостя на слот и показывать встречи владельцу. В этом репозитории агент не пишет новый продукт с нуля: берёт задачи из плана, разбирает их в issue и закрывает pull request’ами.

Каждая задача ниже — кандидат в GitHub Issue. Тип `bug` или `feat` совпадает с Conventional Commits.

## Уже сделано

- Контракт TypeSpec / OpenAPI в `api-contract/`
- Гостевой путь: типы → календарь → слот → подтверждение
- Кабинет владельца: встречи и создание типов событий
- Занятость слотов на сервере, включая пересечения разных типов
- Playwright e2e, Docker-образ на `PORT`, деплой на Render

## Баги

Это правки, которые агент сможет закрыть отдельными PR.

1. **Подтверждение пропадает при обновлении страницы.** `/booked` читает запись только из `location.state`. F5 или прямая ссылка показывают «Запись не найдена», хотя бронь уже создана. Нужен переход с id и `GET` брони (или хотя бы устойчивое сообщение без потери контекста).
2. **Конфликт слота плохо виден в UI.** При `409 SLOT_OCCUPIED` показывается toast, список слотов не обновляется. Гость может нажать «Подтвердить» ещё раз на то же время. Нужен явный текст ошибки на форме и повторный запрос свободных слотов.
3. **Данные живут только в памяти.** Перезапуск контейнера или деплой стирает типы и встречи, остаются только seed `intro-call` и `demo`. Для демо это ожидаемо, для сопровождения — баг: нужен файл или другая персистентность на диске контейнера.
4. **Подпись «Локальное время» при слотах в UTC.** Гость видит часы в своём поясе, API и владелец работают в UTC. Легко записаться не на тот час. Нужна явная подпись пояса (UTC или пояс браузера) на календаре и в подтверждении.
5. **Доступность главной и календаря.** Нет уникальных `title` у страниц, у дней календаря слабые имена для скринридера. Это мешает и людям, и ночному Lighthouse.

## Фичи

Небольшой бэклог, чтобы агент вёл цикл issue → PR, не раздувая продукт.

1. **Отмена предстоящей встречи владельцем.** Кнопка в таблице «Встречи», слот снова свободен. Нужны метод в контракте, API и строка в UI.
2. **Комментарий гостя при записи.** Необязательное поле в форме и в карточке подтверждения / в таблице владельца. Уже заложено в Cal.com-сценарии, в MVP не делали.
3. **Заголовок вкладки по странице.** Например: «Знакомство — Call Booking», «Предстоящие встречи — Call Booking». Удобно для людей и для Lighthouse SEO.

## Как агент берёт задачи

1. Issue из этого плана: заголовок, тип (`bug`/`feat`), шаги воспроизведения или критерий готовности.
2. Комментарий агенту: разобрать, оценить объём, предложить план (triage).
3. PR в отдельной ветке, Conventional Commits, e2e не ломаем.
4. Ревью → правки тем же агентом в том же PR.
5. По расписанию — Lighthouse отдельным workflow (ночь + ручной запуск), отчёт в артефактах Actions, выводы в [`docs/lighthouse.md`](lighthouse.md).

Первыми в работу: баг 2 (конфликт слота в UI) и баг 1 (подтверждение после обновления). Они закрывают замечания к пользовательскому сценарию и дают короткий цикл PR + ревью. Фича 1 (отмена) — следующий issue, когда нужна новая функциональность в контракте.
